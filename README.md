# منصة إدارة مشاريع ومنح الجمعيات الخيرية

منصة ويب متكاملة مخصصة لموظفي الجمعيات الخيرية المسؤولين عن إعداد المشاريع ورفع طلبات الدعم والمنح إلى الجهات المانحة. تساعد المنصة على إدارة المشاريع، رصد فرص التمويل، إدارة الجهات المانحة، إعداد طلبات المنح خطوة بخطوة، متابعة حالتها، وتوليد التقارير — مع مساعد ذكاء اصطناعي مدمج لصياغة ومراجعة المحتوى.

> **ملاحظة حول الإصدار السابق**: كان هذا المستودع يحتوي على نموذج أولي بسيط (صفحة HTML واحدة تعمل بالكامل داخل المتصفح وتحفظ البيانات في LocalStorage). تمت إعادة بناء المنصة بالكامل لتصبح تطبيق ويب حقيقي بقاعدة بيانات وخادم ونظام صلاحيات، مع الإبقاء على نفس الفكرة والهوية العامة (جمعية رفاق الخيرية كبيانات تجريبية).

## 1. التقنيات المستخدمة ولماذا

| الطبقة | التقنية | السبب |
|---|---|---|
| الواجهة والخادم | **Next.js 14 (App Router) + React 18 + TypeScript** | إطار عمل مفتوح المصدر ناضج يجمع الواجهة والـ API في مشروع واحد، يدعم SSR لأداء أفضل، ومناسب جدًا لتطبيقات لوحات التحكم بمنطق خادم كثيف (Server Actions). |
| التنسيق | **Tailwind CSS** | نظام تصميم مرن يسهّل بناء واجهة مؤسسية متجاوبة وموحدة بسرعة، ويدعم RTL بسهولة. |
| قاعدة البيانات | **SQLite عبر Prisma ORM** | قاعدة بيانات ملف واحد لا تحتاج أي خادم أو تكلفة، مثالية للتشغيل المحلي فورًا، مع إمكانية الترقية لاحقًا إلى PostgreSQL/MySQL بتغيير سطر واحد في المخطط لأن Prisma يجرد طبقة الاتصال بقاعدة البيانات. |
| المصادقة | **جلسات JWT موقّعة (مكتبة jose) + bcrypt** | حل خفيف ومملوك بالكامل للمشروع (بدون الاعتماد على خدمة خارجية أو مزود مصادقة سحابي)، يعمل بأمان مع Edge Middleware لحماية الصفحات. |
| الذكاء الاصطناعي | **طبقة مزوّد مستقلة (Mock + أي واجهة متوافقة مع OpenAI)** | تفصل منطق الذكاء الاصطناعي عن الواجهة، تعمل بدون أي مفتاح افتراضيًا (وضع تجريبي محلي)، ويمكن ربطها بأي مزود مجاني أو مفتوح المصدر لاحقًا. |
| الأيقونات | **lucide-react** | مكتبة أيقونات مفتوحة المصدر خفيفة وشائعة الصيانة. |

كل هذه التقنيات مفتوحة المصدر، ولا تتطلب أي اشتراك مدفوع لتشغيل المنصة محليًا.

### لماذا لم يُستخدم مخطط Lovable الأصلي؟
كان المشروع المرفق (Lovable / TanStack Start + Supabase Cloud) موجّهًا لإدارة علاقات الداعمين بشكل عام (Donor CRM) ومرتبطًا ببنية سحابية خاصة بـ Lovable (مصادقة سحابية، Supabase مُدار). تطلبت المتطلبات الجديدة منصة **لإدارة المشاريع وطلبات المنح** لموظفي الجمعيات تحديدًا، بصلاحيات أدوار، وسير عمل مختلف تمامًا لحالة الطلبات، وقابلية تشغيل محلي كامل دون أي خدمة سحابية مدفوعة. لذلك أُعيد البناء من الصفر بمخطط بيانات وواجهات مطابقة للمتطلبات، مع الإبقاء على الروح العامة (هوية جمعية خيرية، فكرة رصد الفرص ومطابقتها، الخطابات كمرفقات).

## 2. بنية المشروع

```
src/
  app/
    (app)/                  # كل الصفحات المحمية (تتطلب تسجيل دخول)
      layout.tsx            # القالب العام: الشريط الجانبي + الشريط العلوي
      dashboard/             # لوحة التحكم
      projects/              # إدارة المشاريع (قائمة/إنشاء/تفاصيل/تعديل)
      opportunities/          # إدارة فرص التمويل
      donors/                 # إدارة الجهات المانحة
      applications/            # طلبات المنح (معالج متعدد الأقسام + متابعة الحالة)
      reports/                # التقارير القابلة للطباعة والتصدير
      settings/users/          # إدارة المستخدمين (لمدير النظام فقط)
    actions/                 # Server Actions (منطق الخادم: إنشاء/تعديل/حذف/تغيير حالة)
    login/                   # صفحة الدخول
    layout.tsx, globals.css  # القالب الجذري و RTL والخطوط
    icon.tsx                 # أيقونة المنصة (تُولَّد برمجيًا، بدون شعار خارجي)
  components/                # مكونات واجهة قابلة لإعادة الاستخدام
  lib/
    ai/                      # طبقة مزوّد الذكاء الاصطناعي (mock + openai-compatible)
    prisma.ts, auth.ts, roles.ts, constants.ts, completion.ts, utils.ts, upload-file.ts
  middleware.ts              # حماية المسارات على مستوى الـ Edge
prisma/
  schema.prisma              # مخطط قاعدة البيانات الكامل
  seed.ts                    # سكربت البيانات التجريبية العربية
public/uploads/              # مجلد تخزين الملفات المرفوعة محليًا
```

### فصل الطبقات
- **العرض (UI)**: مكونات `src/components` و صفحات `src/app/(app)/**/page.tsx`.
- **المنطق/الخادم**: `src/app/actions/*.ts` (تحقق من الصلاحيات، تحقق من صحة البيانات عبر Zod، عمليات قاعدة البيانات، تسجيل النشاط).
- **البيانات**: `prisma/schema.prisma` عبر `src/lib/prisma.ts`.

## 3. الوحدات المنجزة

1. **لوحة التحكم**: عدد المشاريع، فرص التمويل المتاحة، الطلبات قيد الإعداد/المرسلة/المقبولة/المرفوضة، نسبة القبول، متوسط زمن التحضير (من الإنشاء حتى الإرسال)، التمويل المطلوب مقابل المقبول، المواعيد النهائية القريبة (خلال 14 يومًا)، تنبيهات المعلومات الناقصة، مستندات تنتهي صلاحيتها، طلبات متوقفة بلا تحديث، وطلبات تعديل مفتوحة تحتاج إجراء.
2. **إدارة المشاريع**: إنشاء/تعديل/حذف/تكرار، مشكلة، أهداف عامة وتفصيلية، فئة مستفيدة ونطاق جغرافي، أنشطة/مخرجات/نتائج/مؤشرات أداء (حقول ديناميكية قابلة للإضافة والحذف)، جدول زمني وميزانية تفصيلية، رفع مرفقات، حفظ كمسودة.
3. **فرص التمويل**: إضافة/تعديل/حذف، ربط بجهة مانحة أو اسم حر، ربط بمشروع، شروط ومتطلبات، تاريخ بداية ونهاية، رابط تقديم، حالة (مفتوحة/تحت المتابعة/مغلقة)، بحث وتصفية وترتيب، تنبيه بصري عند اقتراب الموعد النهائي (14 يومًا)، وفحص أهلية مبني على شروط قابلة للتعديل من الواجهة (راجع البند 13).
4. **الجهات المانحة**: بيانات الجهة ومجالات الدعم وشروط التمويل وبيانات التواصل وحالة العلاقة، الفرص والمشاريع المرتبطة، ملاحظات ومرفقات — بالإضافة إلى **اكتشاف مانحين جدد آليًا** (بحث يومي بالذكاء الاصطناعي، راجع القسم 7.1)، حيث تظهر المقترحات للمراجعة البشرية قبل إضافتها كمانحين فعليين.
5. **طلبات المنح**: معالج بأقسام (تبويبات) يغطي كل العناصر الـ 16 المطلوبة (الملخص التنفيذي، تعريف الجمعية، وصف المشكلة، المبررات، الأهداف، الفئة المستفيدة، خطة التنفيذ، الأنشطة، المخرجات، النتائج، المؤشرات، إدارة المخاطر، الاستدامة، الجدول الزمني، الميزانية، متطلبات الجهة المانحة) + نسبة اكتمال محسوبة تلقائيًا وقائمة بالعناصر الناقصة.
6. **متابعة الطلبات**: 8 حالات (مسودة، تحت المراجعة الداخلية، جاهز للإرسال، تم الإرسال، مطلوب استكمال، مقبول، مرفوض، مؤجل) مع سجل كامل لكل تغيير (من/إلى، ملاحظة، الخطوة التالية، المستخدم، التاريخ).
7. **التقارير**: 8 تقارير (المشاريع، فرص التمويل، الطلبات المرسلة، نسب القبول، الجهات المانحة، المواعيد النهائية، الميزانيات، أداء الموظفين) قابلة للطباعة (`window.print`) وللتصدير كملف CSV متوافق مع Excel (بترميز UTF-8 مع BOM لدعم العربية).
8. **مساعد الذكاء الاصطناعي**: مدمج داخل نماذج المشاريع والطلبات (صياغة الملخص التنفيذي، تحسين وصف المشكلة، اقتراح أهداف/أنشطة/مخرجات/مؤشرات، مراجعة الترابط والتناقض، إعادة الصياغة الرسمية، تلخيص شروط الفرصة، المقارنة مع شروط الجهة المانحة، تقييم جاهزية الطلب). **لا يختلق بيانات غير موجودة** — يوضح دائمًا عند نقص المعلومات ويطلب إدخالها.
9. **الصلاحيات**: 5 أدوار (مدير النظام، مدير الجمعية، مسؤول المنح، مراجع، مراجع مالي) مع حماية فعلية على مستوى الصفحات والإجراءات (وليس فقط الواجهة) — راجع القسم 8.
10. **رفع الملفات**: مرفقات للمشاريع والطلبات والجهات المانحة، تحقق من النوع (PDF/Word/Excel/صور) والحجم (10 ميجابايت افتراضيًا) على الخادم.
11. **مراجعة طلبات المنح**: تعليقات مرتبطة بحقل محدد أو عامة، نوعان (ملاحظة/طلب تعديل — طلب التعديل يتطلب صلاحية مراجعة)، حالة مفتوحة/معالَجة، وسجل إصدارات تلقائي لكل حفظ للمحتوى مع نافذة مقارنة بين أي إصدار سابق والمحتوى الحالي واستعادة إصدار قديم (تُحفظ الحالة الراهنة كنسخة قبل أي استعادة).
12. **التصدير**: تصدير الطلب كاملًا إلى Word (.docx)، تصدير بنود ميزانية المشروع إلى Excel (.xlsx)، وصفحة طباعة/PDF عبر متصفح المستخدم (`window.print`) بتنسيق عربي يمين-لليسار نظيف بلا عناصر واجهة زائدة.
13. **ملف الجمعية المركزي ومكتبة المستندات**: بيانات الترخيص والنشاط والتواصل والمفوض والبيانات المالية ومجلس الإدارة/الفريق التنفيذي في مكان واحد (بدل إعادة إدخالها في كل طلب)، ومكتبة مستندات مركزية بتصنيفات وتواريخ انتهاء وتنبيهات صلاحية، تُستخدم أيضًا كمصدر لمحرك الأهلية.

### ما لم يُنفَّذ / قيود متبقية
- الاكتشاف الآلي للمانحين (البند 4) يقترح **مانحين محتملين**، لا فرص تمويل محددة الشروط — تسجيل فرصة تمويل رسمية بشروطها الكاملة لا يزال يدويًا، لأن دقة الشروط (مبالغ، مواعيد، مستندات مطلوبة) تتطلب مراجعة بشرية لا يصح الاعتماد فيها على استخلاص آلي وحده.
- إشعارات البريد الإلكتروني للمواعيد النهائية غير مُفعّلة (تظهر كتنبيهات داخل المنصة فقط) — يمكن إضافتها لاحقًا عبر خدمة بريد مجانية (مثل Resend المجاني أو SMTP).
- تصدير التقارير حاليًا بصيغة CSV (تُفتح مباشرة في Excel) وطباعة المتصفح لصيغة PDF؛ تصدير طلبات المنح متاح بصيغتي Word وExcel (البند 12)، لكن لا يوجد توليد PDF مخصص من الخادم — الطباعة تعتمد على متصفح المستخدم (`window.print`) لضمان دعم صحيح للعربية RTL بدون تعقيد إضافي.
- ميزات الذكاء الاصطناعي الحقيقية (غير التجريبية) تتطلب مفتاح API من مزود خارجي (اختياري تمامًا، راجع القسم 6).

## 4. التثبيت والتشغيل محليًا

### المتطلبات
- Node.js 18 أو أحدث (تم البناء والاختبار على Node 22).
- npm (مضمن مع Node).
- لا حاجة لأي قاعدة بيانات خارجية أو حساب سحابي.

### خطوات التشغيل

```bash
# 1. تثبيت الحزم
npm install

# 2. إعداد متغيرات البيئة
cp .env.example .env
# لا حاجة لتعديل أي قيمة للتشغيل المحلي الأساسي

# 3. إنشاء قاعدة البيانات (SQLite محلي، ملف dev.db)
npm run db:push

# 4. تعبئة البيانات التجريبية العربية (جمعية، مستخدمون، مشاريع، فرص، طلبات)
npm run db:seed

# 5. تشغيل خادم التطوير
npm run dev
```

افتح المتصفح على: **http://localhost:3000**

### أوامر قاعدة البيانات
```bash
npm run db:push    # مزامنة مخطط Prisma مع قاعدة البيانات
npm run db:seed    # تعبئة/إعادة تعبئة البيانات التجريبية (تحذف التجريبية القديمة أولًا)
npm run db:reset   # إعادة إنشاء القاعدة من الصفر + تعبئة تجريبية (للتطوير فقط)
```

### البناء للإنتاج
```bash
npm run build
npm run start
```

ملف `.env.example` (انسخه إلى `.env`):

```bash
DATABASE_URL="file:./dev.db"       # قاعدة بيانات SQLite محلية
AUTH_SECRET="..."                   # مفتاح تشفير الجلسات — غيّره في الإنتاج
AI_PROVIDER="mock"                  # mock | openai
AI_API_KEY=""                       # مطلوب فقط عند AI_PROVIDER=openai
```

## 7. تشغيل ميزات الذكاء الاصطناعي

المنصة تعمل بكامل ميزاتها **بدون أي مفتاح API** عبر "الوضع التجريبي" (`AI_PROVIDER=mock`، وهو الافتراضي). في هذا الوضع تُنتَج اقتراحات وصياغات مبنية على المدخلات الفعلية فقط (بدون اختلاق بيانات)، مع رسالة توضيحية أن النتيجة تجريبية.

### لتفعيل مزود ذكاء اصطناعي حقيقي
الطبقة مبنية على واجهة متوافقة مع OpenAI Chat Completions API، فتعمل مع أي مزود يوفرها، مثل:

- **Groq** (له خطة مجانية سخية وسرعة عالية): `AI_BASE_URL="https://api.groq.com/openai/v1"`, `AI_MODEL="llama-3.1-8b-instant"`
- **Ollama** (تشغيل نموذج محليًا مجانًا بالكامل): ثبّت [Ollama](https://ollama.com)، شغّل `ollama pull llama3.1`، ثم اضبط `AI_BASE_URL="http://localhost:11434/v1"` و `AI_API_KEY="ollama"` (أي قيمة غير فارغة)
- **OpenAI الرسمي**: اترك `AI_BASE_URL` فارغًا واضبط `AI_API_KEY` بمفتاحك

ثم اضبط `AI_PROVIDER="openai"` في `.env` وأعد تشغيل الخادم.

### معالجة الأخطاء
عند انتهاء الحد المجاني (429)، انقطاع الاتصال، أو أي خطأ من المزود، تتحول المنصة تلقائيًا إلى نتيجة تجريبية بديلة مع رسالة توضح السبب — لا يتعطل أي إجراء في المنصة بسبب فشل خدمة الذكاء الاصطناعي.

### 7.1 اكتشاف المانحين الآلي (بحث يومي بالذكاء الاصطناعي)

بحث يومي تلقائي عن جهات مانحة جديدة، يستخلص بياناتها الأساسية، يقارنها بمشاريع الجمعية النشطة ويقترح الأنسب لرفعه لها، ويلاحظ أي توجه عام — كل ذلك يُحفظ كـ**مقترح** (`DonorLead`) بانتظار مراجعة بشرية في صفحة "الجهات المانحة"، ولا يُدرج أي بيانات في جدول المانحين الفعلي تلقائيًا (زر "إضافة كمانح" يدوي دائمًا)، التزامًا بقاعدة "لا يختلق المساعد بيانات ولا يعدّل سجلات معتمدة دون مراجعة".

**كيف يعمل**: بحث عبر مزود بحث ويب (`SEARCH_PROVIDER`) → لكل نتيجة، استخلاص بالذكاء الاصطناعي مبني حصرًا على نص النتيجة (`AI_PROVIDER`) → حفظ المقترحات ذات الصلة فقط، مع تجاهل التكرار مع مانحين/مقترحات موجودين مسبقًا.

**التفعيل** (اختياري تمامًا — الوضع التجريبي `mock` يعمل بدون أي مفتاح ويعرض مقترحات توضيحية واضحة المصدر):
1. أنشئ حسابًا مجانيًا على [tavily.com](https://tavily.com) واحصل على مفتاح API.
2. اضبط في متغيرات البيئة: `SEARCH_PROVIDER="tavily"`، `SEARCH_API_KEY="<مفتاحك>"`.
3. اضبط `CRON_SECRET` بقيمة عشوائية طويلة — يحمي نقطة `/api/cron/discover-donors` من الاستدعاء الخارجي (Vercel يرسلها تلقائيًا كترويسة عند تشغيل المهمة المجدولة).
4. الجدولة اليومية مضبوطة مسبقًا في `vercel.json` (الساعة 3:00 صباحًا UTC) — لا حاجة لإعداد إضافي على Vercel.

يمكن أيضًا تشغيل البحث يدويًا في أي وقت بزر "تشغيل البحث الآن" في صفحة الجهات المانحة (لمن يملك صلاحية تعديل السجلات).

## 8. الصلاحيات والأدوار

| الدور | الصلاحيات |
|---|---|
| **مدير النظام** (ADMIN) | كل الصلاحيات + إدارة المستخدمين والأدوار |
| **مدير الجمعية** (ORG_MANAGER) | إشراف كامل على المشاريع/الفرص/الجهات/الطلبات + حذف السجلات + التقارير |
| **مسؤول المنح** (GRANTS_OFFICER) | إنشاء وتعديل المشاريع والفرص والجهات والطلبات، تغيير حالة الطلبات |
| **مراجع** (REVIEWER) | عرض جميع البيانات دون تعديل مباشر للمحتوى، مع إمكانية تغيير حالة الطلب وكتابة ملاحظات المراجعة |
| **مراجع مالي** (FINANCE_REVIEWER) | مراجعة الميزانيات والجوانب المالية للطلبات |

تُطبَّق هذه الصلاحيات على مستوى **الخادم** (داخل كل Server Action) وليس فقط بإخفاء عناصر الواجهة، لمنع أي التفاف على الحماية. مصفوفة الصلاحيات معرّفة في مكان واحد (`src/lib/authz-matrix.ts`) ويستخدمها الخادم والواجهة معًا.

### عزل بيانات الجمعيات (Multi-tenancy)

كل سجل في المنصة مرتبط بـ`organizationId`، وكل استعلام يمر عبر نقطة إنفاذ مركزية في `src/lib/authz.ts`:

- صفحات التفاصيل تستخدم `findFirst` مقيّدًا بالجمعية بدل `findUnique` بالمعرّف — أي أن تخمين رابط سجل من جمعية أخرى يُنتج **404** لا محتواه.
- القوائم والتقارير ولوحة التحكم والقوائم المنسدلة كلها مقيّدة بجمعية المستخدم.
- لأن `organizationId` إلزامي عند الإنشاء، **يرفض TypeScript أي كتابة غير مقيّدة وقت الترجمة**.
- **فصل المهام**: الاعتماد النهائي يتطلب صلاحية `finalApproval`، ولا يستطيع المستخدم اعتماد طلب أنشأه بنفسه.

يتحقق ملف `tests/e2e/tenancy.spec.ts` من ذلك عمليًا عبر جمعية ثانية في البيانات التجريبية.

يقوم الإعداد (`playwright.config.ts`) تلقائيًا بإعادة تهيئة قاعدة البيانات وتعبئتها بالبيانات التجريبية، ثم تشغيل خادم التطوير، قبل تنفيذ الاختبارات — لا حاجة لأي إعداد يدوي مسبق. عند التشغيل لأول مرة قد تحتاج لتثبيت متصفح Chromium الخاص بـ Playwright:

```bash
npx playwright install chromium
```

> إن كانت بيئتك توفر متصفح Chromium مثبّتًا مسبقًا في مسار مخصص (كبعض بيئات CI)، مرّر مساره عبر `PLAYWRIGHT_CHROMIUM_PATH=/path/to/chromium npm run test:e2e` بدل تثبيت نسخة جديدة.

هذه المجموعة اكتشفت فعليًا خللًا حقيقيًا أثناء التطوير (فقدان بيانات التبويبات غير النشطة في نموذج طلب المنحة عند الحفظ) وتم إصلاحه بفضلها — وهي تُشغَّل بالكامل (26 اختبارًا) بنجاح على النسخة الحالية.

### فصل بيئة العرض التجريبي عن الإنتاج

- بطاقة الحسابات التجريبية في صفحة الدخول **لا تظهر في الإنتاج**؛ تحتاج `SHOW_DEMO_ACCOUNTS=true` صراحةً.

### اختبارات يدوية إضافية

## 10. ملاحظات أمنية وأداء

- كلمات المرور مُشفّرة بـ bcrypt (10 rounds)، ولا تُخزَّن أبدًا كنص صريح.
- الجلسات عبر JWT موقّع بمفتاح سري من متغيرات البيئة، مخزّن في كوكي `httpOnly` (غير قابل للقراءة من JavaScript في المتصفح) و`sameSite=lax`.
- كل عمليات الكتابة (إنشاء/تعديل/حذف/تغيير حالة) تمر عبر Server Actions تتحقق من الجلسة والصلاحية قبل أي وصول لقاعدة البيانات.
- التحقق من صحة المدخلات عبر Zod على الخادم (بالإضافة إلى تحقق HTML الأساسي في الواجهة)، مع رسائل خطأ عربية واضحة.
- رفع الملفات يتحقق من نوع الملف (Whitelist صريح) وحجمه على الخادم قبل الحفظ، ويولّد اسم ملف عشوائيًا لتفادي تعارض الأسماء أو تنفيذ ملفات ضارة.
- لا توجد أسرار أو مفاتيح API داخل الكود المصدري؛ كل القيم الحساسة عبر `.env` (غير مرفوع لأي مستودع).
- استعلامات قاعدة البيانات عبر Prisma (معاملات مُجهّزة تلقائيًا) لمنع حقن SQL.
- صفحات القوائم تدعم البحث والتصفية والترتيب وتقسيم النتائج إلى صفحات لتفادي تحميل بيانات كبيرة دفعة واحدة.

## 11. النشر السحابي المجاني (Vercel + Turso + Vercel Blob)

المنصة قابلة للنشر مجانًا بالكامل (بدون أي رسوم) على حزمة مكوّنة من ثلاث خدمات مجانية معروفة، دون أي تعديل إضافي في الكود — الدعم مبني فيه مسبقًا (وضع مزدوج: محلي/سحابي يتفعّل تلقائيًا حسب متغيرات البيئة):

| الحاجة | الخدمة | السبب |
|---|---|---|
| استضافة التطبيق | **Vercel** (خطة Hobby المجانية) | تكامل رسمي ومباشر مع Next.js، نشر تلقائي من GitHub، شهادة HTTPS مجانية |
| قاعدة البيانات | **Turso** (الخطة المجانية) | قاعدة بيانات متوافقة مع SQLite بالكامل (نفس محرك المشروع)، تعمل عبر مهايئ Prisma الرسمي دون تغيير المخطط |
| تخزين المرفقات | **Vercel Blob** (الخطة المجانية) | التخزين المحلي لا يبقى بين عمليات النشر على استضافة بدون قرص دائم مثل Vercel؛ Blob يحل هذا مجانًا |

> **لماذا لا تكفي استضافة Vercel وحدها؟** خوادم Vercel بلا حالة (Serverless) — أي ملف SQLite محلي أو مرفق مرفوع يُفقد عند كل نشر جديد أو حتى بين الطلبات. لذلك تحتاج قاعدة بيانات وتخزين ملفات "مُدارين" خارجيًا، وكلاهما مجاني هنا.

### خطوات النشر

1. **إنشاء قاعدة بيانات Turso**: أنشئ حسابًا مجانيًا على [turso.tech](https://turso.tech) (تسجيل عبر GitHub متاح)، ثم أنشئ قاعدة بيانات جديدة. انسخ قيمتي **Database URL** (تبدأ بـ `libsql://`) و **Auth Token**.

2. **استيراد المشروع في Vercel**: من [vercel.com](https://vercel.com) اختر "Add New Project" واربط مستودع GitHub هذا. يكتشف Vercel أنه مشروع Next.js تلقائيًا.

3. **إنشاء مخزن Vercel Blob**: من تبويب Storage داخل مشروع Vercel، أنشئ "Blob Store" واربطه بالمشروع — سيضيف Vercel متغير `BLOB_READ_WRITE_TOKEN` تلقائيًا.

4. **ضبط متغيرات البيئة** في إعدادات المشروع على Vercel (Settings → Environment Variables):
   ```
   TURSO_DATABASE_URL=libsql://<اسم-قاعدتك>.turso.io
   TURSO_AUTH_TOKEN=<التوكن>
   AUTH_SECRET=<قيمة عشوائية طويلة، مثل ناتج openssl rand -base64 32>
   AI_PROVIDER=mock
   BOOTSTRAP_SECRET=<قيمة عشوائية مؤقتة، لمرة واحدة>
   ```
   (لا حاجة لضبط `DATABASE_URL` أو `BLOB_READ_WRITE_TOKEN` يدويًا — الأول غير مُستخدم في وضع Turso، والثاني يُضاف تلقائيًا من خطوة 3.)

5. **النشر**: اضغط Deploy. عند اكتمال البناء ستكون المنصة متاحة على رابط `https://<اسم-مشروعك>.vercel.app`.

6. **تهيئة قاعدة البيانات لمرة واحدة**: قاعدة Turso فارغة (بلا جداول) بعد الإنشاء مباشرة — استدعِ نقطة التهيئة المدمجة مرة واحدة بعد أول نشر لإنشاء الجداول وتعبئة بيانات تجريبية:
   ```bash
   curl -X POST https://<اسم-مشروعك>.vercel.app/api/admin/bootstrap \
     -H "x-bootstrap-secret: <نفس-قيمة-BOOTSTRAP_SECRET>"
   ```
   هذه النقطة آمنة لإعادة الاستدعاء: تُنشئ الجداول فقط إن لم تكن موجودة، ولا تُعبّئ بيانات تجريبية إن وُجدت بيانات حقيقية بالفعل (تتحقق أولًا من أن جدول المستخدمين فارغ). بعد التنفيذ الناجح، يمكن حذف `BOOTSTRAP_SECRET` من متغيرات البيئة على Vercel لتعطيل النقطة تمامًا.

### تحديثات لاحقة
أي `git push` إلى `main` يُعيد نشر المنصة تلقائيًا على Vercel. لكن نشر الكود وحده **لا يُحدّث مخطط قاعدة بيانات Turso تلقائيًا** — Prisma CLI لا يمكنه استهداف رابط Turso مباشرة، لذلك يُطبَّق أي تعديل على `prisma/schema.prisma` يدويًا عبر إعادة استدعاء نقطة التهيئة:

```bash
curl -X POST https://<اسم-مشروعك>.vercel.app/api/admin/bootstrap \
  -H "x-bootstrap-secret: <نفس-قيمة-BOOTSTRAP_SECRET>"
```

**هذه الخطوة إلزامية بعد كل تحديث يضيف جدولًا أو عمودًا جديدًا** (مثل إصدار تعدد الجمعيات، أو ملف الجمعية المركزي، أو تعليقات المراجعة وسجل الإصدارات) — وليست مقصورة على أول نشر:
- إن كانت `BOOTSTRAP_SECRET` قد حُذفت من متغيرات البيئة بعد أول استخدام (كما هو موصى به)، أعد إضافتها مؤقتًا في Vercel، أعد النشر حتى تُطبَّق، ثم استدعِ النقطة، ثم احذفها مجددًا.
- النقطة آمنة التكرار: تُنشئ أي جدول ناقص بالكامل، ثم تضيف أي عمود ناقص لجدول موجود مسبقًا (عبر `ALTER TABLE`) وتُعبّئه تلقائيًا من البيانات القائمة عند الحاجة (مثل ربط كل السجلات القديمة بمعرّف الجمعية الوحيدة التي كانت موجودة قبل تعدد الجمعيات) — لا تحذف أو تكرر أي بيانات حقيقية، وتتجاهل تلقائيًا أي عمود مطبَّق مسبقًا.
- الاستجابة تتضمن `migrationLog` يوضح كل عبارة تحديث ونتيجتها (`applied` أُضيفت الآن، `already_applied` كانت مطبَّقة، `error` تحتاج مراجعة).

عند إضافة حقول أو جداول جديدة مستقبلًا لـ `prisma/schema.prisma`، حدِّث `TURSO_CREATE_TABLES_SQL` (للتركيبات الجديدة) و`TURSO_MIGRATE_STATEMENTS` (للترقية التدريجية) يدويًا في `src/lib/turso-init-sql.ts` وفق الشرح أعلى الملف، ثم استدعِ `/api/admin/bootstrap` كما سبق.
